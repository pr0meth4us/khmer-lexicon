What this is

A searchable dictionary of Cambodian government terminology — the approved Khmer renderings of technical, legal, economic and administrative terms. {{ '{:,}'.format(about.entries) }} entries from {{ sources|length }} official sources (where they came from). Until now this existed almost entirely as scanned paper: a person could look a term up, a program could not.

It was built by running Google Cloud Vision OCR over the source PDFs, parsing the results into structured entries, then normalising and merging them. None of that runs when you use the site — the dictionary is a static file, so there are no API keys, no database, and nothing to fail during use.

Why you don't have to type it perfectly

Khmer is hard to type correctly, so an exact-match dictionary tells most people “not found” when the word is sitting right there. If nothing matches exactly, we look for entries one grapheme cluster away — one Khmer syllable, not one byte — and offer those instead.

This is not a spell checker, and it never judges your spelling. It forgives an imperfect query so you can reach an entry. Checking whether Khmer prose is spelled correctly needs a dictionary of general vocabulary; this is a dictionary of {{ '{:,}'.format(about.entries) }} official terms, and checking ordinary writing against it would mark almost every normal word as wrong.

Working in clusters rather than characters matters because a Khmer syllable is several code points. ក្រសួង is 6 code points but 3 clusters: ក្រ | សួ | ង. Measuring distance in code points would call two words similar that a reader would never confuse, and miss two that they would.

Why checking a letter is fast

Looking for {{ '{:,}'.format(about.terms_indexed) }} terms one at a time means reading the whole letter {{ '{:,}'.format(about.terms_indexed) }} times. Instead all the terms are compiled into a single structure (Aho–Corasick) that finds every one of them in one pass, so the cost depends on the length of your letter, not on the size of the dictionary.

Measured on this data: the naive approach takes about 7.7 ms and grows with every term added; the single pass takes about 0.3 ms and stays flat from 250 terms to 5,780. Below roughly 220 terms the naive approach is genuinely faster, which is worth saying rather than hiding.

Khmer has no spaces between words, so a dictionary match can land inside a longer unrelated word — ប្រក sitting inside ប្រកាស (“announce”). Matches are filtered twice: they must sit on syllable boundaries, and they must line up with word boundaries from a CRF word segmenter. Syllable boundaries alone are not enough; that was measured, not assumed.

The invisible-character problem

Some characters look exactly like Khmer letters but are not. A Devanagari or Thai vowel sign can sit in the middle of a Khmer word and be completely invisible on screen, yet the word will never again be found by a search, sort correctly, or match its own duplicate. These are detected using Unicode's own data — both letters that share a Unicode name across scripts, and the published confusables list — plus a catch-all for any character from a script that doesn't belong, which is how a stray Cyrillic letter was found in the source data.

How accurate is this? About one Khmer headword in five is wrong

Every entry here was produced by running optical character recognition over a scanned paper document, then having a language model parse the messy output into structured fields. Both steps make mistakes. Treat it as a research tool and a finding aid, not as an authoritative citation.

Beyond that sample, the build counts what a program can see: {{ ev.known_defects.near_duplicate_pairs }} pairs that look like one term spelled two ways, {{ ev.known_defects.one_misread_from_a_dictionary_word }} single-word terms one misread from a Royal Academy dictionary word, and {{ '{:,}'.format(ev.known_defects.missing_english) }} entries with no English. An OCR mistake that turns one real Khmer word into another is invisible to all of those checks, which is why the sample matters.

What it can't do

  • It covers terminology, not vocabulary. ក្រសួង (“ministry”) is not an entry, because no glossary defined it. Common words will often return nothing.
  • {{ '{:,}'.format(ev.known_defects.missing_english) }} entries have no English. They came from Khmer-only documents. They're still searchable in Khmer, and we say so rather than showing a blank.
  • {{ '{:,}'.format(coverage[3][1]) }} of {{ '{:,}'.format(about.entries) }} entries ({{ '{:.0%}'.format(coverage[3][2]) }}) carry a Khmer definition, and {{ '{:,}'.format(coverage[5][1]) }} carry usage examples. Coverage is uneven by source: every NCKL bulletin entry has one, but the Pentagonal Strategy glossary is a term list with no definitions at all, and only 9% of place names have one. Entries without a definition say so rather than looking empty.
  • It finds known terms; it cannot discover new ones. If a term isn't in the lexicon, nothing will tell you it was a term.
  • Its accuracy has not been formally measured. The boundary filters demonstrably remove wrong matches, but no one has annotated a test set and scored it. That's the most valuable next piece of work.
  • The source data has known defects, listed openly below.

Known defects in the data

  • {{ ev.known_defects.missing_khmer }} entries have no Khmer form at all.
  • {{ ev.known_defects.khmer_field_with_no_khmer }} entries have a Khmer field containing no Khmer characters — old-font OCR misread as Latin, plus six French grammar terms filed in the wrong column. These are excluded from search results.
  • {{ baseline['duplicate khmer forms'] }} Khmer forms appear more than once, and {{ ev.known_defects.near_duplicate_pairs }} pairs differ by a single syllable and mean the same thing.
  • 23 entries had their marks in a non-standard order and were corrected at build time; Unicode's own normalisation cannot fix this, because almost every Khmer mark is invisible to it.

A validator runs on every build and fails it if any of these counts get worse.
